В результате эксперимента установлено, что использование составного
B-tree индекса существенно влияет на производительность запроса.
Без индекса PostgreSQL использовал Parallel Seq Scan, что приводило к полному просмотру
таблицы transactions. После создания индекса план выполнения изменился на
Bitmap Index Scan и Bitmap Heap Scan, что уменьшило время выполнения запроса.
Наиболее эффективным оказался индекс (type, amount, transaction_date). Это связано с тем,
что PostgreSQL наиболее эффективно использует составные B-tree индексы, когда сначала идут поля
с точным сравнением (больше селективность), а затем поля с диапазонными условиями (меньше селективность).
Индексы, начинающиеся с диапазонных условий, показали худшие результаты,
поскольку после первого диапазонного условия эффективность использования последующих колонок снижается.

Parallel Seq Scan - полное сканирование всей таблицы (1 001 000 строк) для фильтрации по `type = 'expense'`.

ГИПОТЕЗА:

Создание индекса, включающего колонки `type` (для фильтрации) и `amount` (для сортировки),
позволит:

- получить строки уже в отсортированном порядке (без Sort);
- применить LIMIT без обработки всех строк.
Предполагается, что индекс `(type, amount DESC)` будет наиболее эффективным,
так как направление сортировки совпадает с порядком в индексе.

ВЫВОД:

В результате эксперимента установлено, что использование индекса для запроса с ORDER BY и LIMIT
даёт существенно больший выигрыш в производительности по сравнению с запросом со сложным фильтром.
Это объясняется разным объемом возвращаемых данных (1001000 против 10), разными типами операций (поиск по диапазону
против точного совпадения и сортировки), особенностями заполнения таблиц (2 типа транзакций, 4 типа amount -

Наиболее эффективными оказались индексы `(type, amount DESC)` и `(type, amount)`:
- ускорение в 520-3600 раз по сравнению с полным сканированием;
- устранение операции сортировки (Sort);
- использование Index Scan вместо Seq Scan;
- минимальное количество чтений с диска (4-8 блоков вместо 16 000+).
Вариант с индексом `(type, amount)` показал даже лучший результат (0.049 ms),
чем вариант с явным DESC (0.339 ms), что объясняется особенностями оптимизатора PostgreSQL.
Индекс только по `amount` оказался неэффективным, так как требует дополнительной фильтрации
по `type` и отбрасывает 500 500 строк, что практически равно времени выполнения без индекса.
Для запросов с ORDER BY и небольшим LIMIT индекс даёт колоссальный выигрыш,
так как позволяет прекратить сканирование после нахождения нужного количества строк,
в отличие от запросов, возвращающих большой процент строк.

ВЫВОД:

В результате эксперимента установлено, что для данного запроса
наиболее эффективным оказался B-Tree индекс на `transaction_date`,
а не специализированные GIN индексы для текстового поиска.
Причины:
1. B-Tree индекс обеспечивает одновременно фильтрацию по дате (Index Cond),
сортировку в нужном порядке (Index Scan Backward),
возможность раннего прекращения сканирования (LIMIT).
2. GIN индексы (tsvector, trgm) эффективно находят строки по тексту,
но возвращают слишком много строк, требуя последующей сортировки,
что сводит на нет выигрыш от текстового поиска.
3. PostgreSQL выбрал план с B-Tree индексом даже при наличии обоих индексов,
что подтверждает правильность выбора оптимизатора.
Итоговое ускорение: 270-340 раз (с 536 ms до 1.6-2.0 ms).
Выбор типа индекса должен основываться на анализе полного запроса,
а не только на отдельных условиях. GIN индексы хороши для текстового поиска,
но если запрос также требует сортировки по другому полю, B-Tree индекс
может оказаться эффективнее за счёт устранения операции сортировки
и возможности раннего прекращения сканирования (при LIMIT).

При низкой селективности (возврате большого процента строк) последовательное
сканирование может быть эффективнее
из-за меньших накладных расходов на случайный доступ к таблице.

АНАЛИЗ УЗКИХ МЕСТ ВЫПОЛНЕНИЯ:

Parallel Seq Scan на transactions - основное узкое место:
отфильтровано 291 181 строк на worker (всего ~873 543 из 1 001 000),
возвращено 42 486 строк, удовлетворяющих условиям (4.2% таблицы), время сканирования 117 ms.
Hash Join операции - время незначительно.
3Sort + GroupAggregate - сортировка и группировка 42 486 строк:
используется внешняя сортировка на диске (temp read/written 326 блоков), время: 50 ms.
Основное время (310 ms из 377 ms) уходит на сканирование transactions.

ГИПОТЕЗА:

Создание индексов на внешних ключах (account_id, category_id) и составного индекса
для фильтрации (type, amount, transaction_date) позволит:
- использовать Index Scan вместо Seq Scan на transactions;
- уменьшить количество строк для последующей обработки;
- избежать создания хеш-таблиц за счёт Nested Loop Join.

ЗАПРОСЫ С ИНДЕКСАМИ:

BEGIN;
CREATE INDEX idx_transactions_account_id ON transactions(account_id);
CREATE INDEX idx_transactions_category_id ON transactions(category_id);
CREATE INDEX idx_transactions_type_amount_date ON transactions(type, amount, transaction_date);

EXPLAIN (ANALYZE, BUFFERS, TIMING, VERBOSE)
SELECT
    u.full_name,
    a.name AS account_name,
    c.name AS category_name,
    COUNT(t.id) AS transaction_count,
    SUM(t.amount) AS total_amount
FROM transactions t
         JOIN accounts a ON t.account_id = a.id
         JOIN users u ON a.user_id = u.id
         JOIN categories c ON t.category_id = c.id
WHERE t.type = 'expense'
  AND t.amount > 100
  AND t.transaction_date >= '2025-01-01'
GROUP BY u.full_name, a.name, c.name
ORDER BY total_amount DESC
    LIMIT 20;

ROLLBACK;

Индексы не были использованы из-за:

ГИПОТЕЗА:

Создание обычного B-Tree индекса на колонке `description` не поможет,
так как B-Tree индекс эффективен только для поиска по префиксу (LIKE 'Purchase%'),
но не для поиска по суффиксу (LIKE '%Purchase').
Для оптимизации такого запроса необходимо использовать специализированный
GIN индекс с расширением pg_trgm, поддерживающий поиск по подстроке.

ВЫВОД:

В результате эксперимента установлено, что обычный B-Tree индекс
не используется для поиска по суффиксу (LIKE '%Purchase').
Причины:
1. B-Tree индекс хранит строки в отсортированном порядке по первому символу;
2. Поиск по суффиксу требует проверки окончания строки, что невозможно
с использованием B-Tree без полного сканирования;
3. Планировщик PostgreSQL выбирает Seq Scan, так как индекс не может
эффективно ответить на запрос.

Без индекса: 96 ms (полное сканирование)
С B-Tree индексом: 100 ms (индекс не используется, небольшое замедление
из-за накладных расходов на поддержку индекса)

Для разных типов поиска нужны разные типы индексов:
1. Префиксный поиск - B-Tree;
2. Суффиксный/подстроковый поиск - GIN с pg_trgm;
3. Полнотекстовый поиск - GIN с tsvector.
